Implementation notes

Where the firmware, DROID patch and written controls differ, what you can do on the instrument today, and what could be improved.

MIDI control assignments are spread across several files

MidiConfig.h defines MIDI channels, note numbers and Control Change (CC) numbers for the legacy firmware. The teensy41-engine target handles incoming MIDI separately. Its Surface::input combines named button assignments with hard-coded channels and CC numbers. EditSurface::value and trigger encode the outgoing MIDI messages for motorized faders. The DROID patch also defines what each physical control transmits and receives.

What a player sees. Changing a pad’s note assignment in the legacy configuration leaves the current engine responding to the original note number. If only the engine’s fader input changes, a fader might edit the correct parameter while its motor still listens for feedback on the previous channel or CC number.

Suggested next step. Start with one engine binding list covering message type, number, channel, direction and editor bank. Have both the input decoder and feedback writers use it. Check the reference patch and publish the manual's MIDI tables against the same list. Test the existing DROID assignments where MIDI notes 1 and 2 on channel 15 serve as both motor triggers and step LED feedback.

Controller presets live outside the device

The firmware matches incoming MIDI messages against fixed assignments. It reserves channels 13–16 for the control surface on all three MIDI inputs. The looper has no MIDI Learn function or editor for controller presets. Assign pads and faders on a programmable controller, or translate their messages with a MIDI router.

What a player sees. A sustain pedal sending CC 64 on channel 1 needs a MIDI translator to act as Record. Map pedal down to Note On 36 on channel 16 and pedal up to Note Off 36 on the same channel. This lets the looper distinguish a tap from a hold.

Suggested next step. If runtime remapping becomes a product goal, define a small first version around one press/release binding with a default to restore. Specify how a learned control on a musical channel is intercepted, how duplicate assignments are handled, and where the profile persists. Test the learned control during recording with MIDI thru and LED feedback enabled.

The four-button base module is incomplete

The intended standalone instrument has four physical buttons and a push encoder. The engine reads the encoder from pins 29 and 30 and its switch from pin 31. You can turn or press it in NOTE_EDIT and GROOVE. The engine does not yet read the four base-module buttons.

What a player sees. Use a MIDI controller for Record, transport, editing mode selection and track changes on this build.

Suggested next step. Bring one physical Record button through the existing gesture handling first. Exercise arm, recording, undo and redo from both input surfaces and compare feedback, then connect the remaining buttons.

The loop picker and the DROID use different Play/Stop messages

The saved-loop picker moves down one row when it receives a tap on note 40, channel 16. With the supplied DROID patch, tapping PLAY/STOP sends note 39 for global transport. Holding it sends note 43 for GROOVE. Pressing the labeled button can start or stop playback while the picker cursor stays in place.

Workaround. Assign a spare momentary pad to note 40 on channel 16. In the picker, use NOTELEN for up, that pad for down, REC for left and EDIT for right.

Suggested next step. Choose the intended control for Down on the reference controller. Align the patch, picker hint and gesture handler, then check that all eight rows can be reached while playback continues.

Guide entries that disagree with current controls

  • Entering an editor. The README's first-session walkthrough says to press Edit to open NOTE_EDIT. A tap actually changes the track row between select and mute. Hold Edit for about 0.6 seconds, then release before 1.5 seconds to enter NOTE_EDIT on a filled loop or LOOP_EDIT on an empty slot. A 1.5-second hold exits editing. First-session walkthrough · Edit gesture handler.
  • GROOVE field navigation. The README gesture table assigns “next field” to a short Transport or Track play/stop press in GROOVE. The current handler ignores both. Use Record for the previous field, Edit for the next, or push the encoder for the next. The separate screen-design guide describes that behavior. README gesture table · Window gesture handler · Screen-design guide.
  • Starting with external MIDI Clock. The fixed-memory guide says the transport button does nothing while the external clock source is stopped. If the source keeps transmitting MIDI Clock while stopped, tapping the looper’s transport button arms a local start. Playback begins on the next incoming clock pulse, which the looper treats as a bar line. Fixed-memory guide · External transport handler.
  • Quantizing notes. The README's feature summary lists quantize as unavailable. Its own GROOVE guide describes the shipped STRAIGHT sixteenth-note template. Choose STRAIGHT and raise the amount to pull recorded notes toward the grid. In GROOVE, TRK toggles AUTO Q to apply the groove when an overdub on that loop ends. The dedicated legacy Quantize button is a separate feature. Feature summary · Groove templates · Engine templates · AUTO Q gesture.

Suggested next step. Give each gesture one maintained description and link to it from the other guides. Distinguish groove timing, slot launch quantization and the retired legacy control in the feature summary.

Milestones and recovery checkpoints omit older card-only undo steps

The storage guide describes a milestone as containing each slot's “full undo history.” The working store can keep older steps on the SD card after they leave memory. The library writer takes its milestone and checkpoint snapshots from History::chain, which walks only the entries in memory. A set load clears both the in-memory history and the slot's older card-only history before installing the snapshot.

What a player sees. A saved milestone includes the loops and the undo steps that were in memory at the time of the save. After loading it, you may see fewer undo steps for a loop. To return to the set you were playing before the load, send !ENGINE return over USB serial. There is no Return row in the sets browser. Its recovery checkpoint has the same undo limit. To recall a particular arrangement later, save it as its own milestone while it is current.

Suggested next step. Specify whether library saves must preserve card-only history. Add a round-trip check with a known card-only step before promising full-history saves. Keep the workspace and milestone guarantees explicit in the storage guide.

Storage guide wording · Snapshot capture · In-memory chain traversal · Clearing cold states during a set replacement · Browser navigation · Serial checkpoint return.

Track output channels are assigned at startup

The output layer can set a MIDI transmit channel per track. At startup, the firmware assigns track 1 to channel 1 through track 8 to channel 8. The looper sends recorded MIDI events through DIN MIDI OUT and the computer-facing USB port. On the USB host port it transmits MIDI feedback to the control surface.

What a player sees. Recording a keyboard on input channel 10 into track 1 produces playback on MIDI channel 1. To play a synth set to receive only on channel 10, change its receive channel or use a MIDI router to remap the track’s output to channel 10.

Suggested next step. If user-selectable routing is wanted, expose the existing channel setting and decide whether it belongs to a set or the device. Test playback, live thru and note releases across a routing change before adding a setup screen.
