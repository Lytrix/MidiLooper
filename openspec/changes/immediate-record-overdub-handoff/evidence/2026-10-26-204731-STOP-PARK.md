`phase=8` is `PendingStopPhase::UndoCollection`. The refusal rows are DEC-078 diagnostics on an
**accepted** stop: the presses were retained, not lost. The defect is that the job never left the
phase on its own.

## Cause (VERIFIED in source)

`Track::stepDeferredUndoCollection` treats a refused or `Denied` session-identity collection as
"collected" (`job.undoCollected = true`, returns true), but the phase gate that follows required

```cpp
if (!job.undoCollectable ||
    job.undoCollection.phase != Loop::SessionUndoCollection::Phase::Cold) return false;
```

and `Cold` is set only by `TrackPreparedUndo::prepareOverdubSessionEntry`, which requires
`Loop::collectedOverdubSessionUndoPassesCurrent` — i.e. a **`Complete`** collection. A refused
collection never becomes `Complete`, and nothing re-clears the refusal, so the gate is permanent.
The job keeps `captureStopOwner`, its frozen role and its session-exit receipt; every later Stop
meets `stop_job_pending`.

Reachable without a fault: `Loop::beginCollectOverdubStopUndoPasses` is qualified by
`preparedCompanionHistory_.revision == playbackRevision` and `firstId == nextPassId_`, so any
successor wrap or publication between `CompanionHistory` and the collection refuses it.

## Repair

Retention is kept (`CaptureStopJob::undoCollectionRetentions`), so a pass still never publishes
without its undo level, but the wait is bounded (`kUndoCollectionRetentionLimit = 512`, DEC-070's
shape for a predicate that can no longer become true). On exhaustion the interval's own session-exit
receipt supplies the identities through the existing
`prepareDeferredOverdubUndoEntryFromReceipt`, which is the same fail-open rule the atomic transfer
applies to an unnamed entry; a receipt that names nothing yields no entry.
