## Formal reassessment — source continuity (proposed, not implementation approval)

- **Trigger:** IMPLEMENTATION_READINESS G3 lifetime-model/resource change. A complete result must remain valid/selectable while a different generation is constructed; current global session clears its only accumulated result on re-key. Do not hide this dependency inside another wakeup tweak.
- **Current architecture:** Loop/LoopContentResolution owns derived-source construction; DisplayManager owns one retained window/prefix. That prefix cannot serve a newly requested wrapped interval it never covered. Existing bounded source is all-pass and re-keyed as a unit; its per-pass `projected` buffer and accumulated `notes` buffer are both used during candidate construction, so a second retained whole-result store cannot be asserted free.
- **Preferred evolution:** extend the existing display representation owner with explicitly generation-qualified current/candidate publication. Preserve a complete source under its own identity/coverage while preparing the requested/wrapped interval ahead of consumption; never stamp old rows as current or stitch incompatible bases. ## Round 2 — revised contract (supersedes the proposal above)

Round-1 findings accepted. Two adjustments adopted by owner direction: **state-generation identity
instead of a per-pass state array** (cardinality-free), and **capacity-priced, fail-closed retention**
(`16·E`, no `shrink_to_fit`). Prose only — no production behaviour changed.

### R1/F1/F2 — invalidation authority

VERIFIED: `Loop::setCapturePassState` increments `playbackRevision` (`src/Loop/LoopCapture.cpp:190`) and
`setEditPassState` does too (`src/TrackUndo.cpp:360`). `playbackRevision` is therefore **overloaded**: a
wrap append also advances it, so requiring revision equality would refuse exactly the case that must be
served, while ignoring it let undone passes satisfy the draft predicate (`boundedDisplayCountCommittedEvents`
sums `committedChunkIds` without reading `state`, `src/LoopContentResolution.cpp:3151`).

**Decision — one monotonic stamp on `Loop`, `passStateRevision_`.**

- Cost: `Loop` objects are external-pool slot shells (`include/LoopPool.h:26`), so `+4 B` is external and
  **RAM1 `variables` is unchanged by construction**.
- Monotonic for the Loop's lifetime; unlike `playbackRevision` it is **never reset to 0`**.
- Bumped only when a transition can invalidate retained content: `setCapturePassState` (record and overdub
  branches, on an actual state change), `setEditPassState` (when `touched`), `resetPassTimeline`, and every
  pass-replacing restore/hydrate/clear path (to be enumerated at implementation; each is a named call site,
  not an assumption).
- Appends do **not** bump it, which is what lets a wrap keep serving.

### Serve predicate (pure, O(P), allocation-free, fail-closed)

(a) `owner`, `loopId`, `loopLengthTicks` equal; (b) `live.passStateRevision == retained.passStateRevision`;
(c) `live.passCount >= retained.passCount`; (d) prefix-live — for each `i < retained.passCount`, the live
resolve-order pass has the same `PassId` **and** the same committed row count; (e) `editPasses.size()` and
last edit id equal; (f) the retained result is whole-loop, so coverage is the existing
`noteIntersectsWindow` filter. Any failure is a **named refusal**, never a relabel; the caller keeps its
honest hole.

### F6 — appended-pass availability (found during round 2)

A wrap's new pass is not in the retained envelope; its closed rows reach paint only through the
`sealedCapturePreviewNotes_` tier (`Loop::retainCapturePreviewAtSeal`) until the committed representation
covers them. That tier is released by `sealedCapturePreviewIsCovered`, whose authority is the visual
cache/committed representation — **not** the retained envelope. So a retained frame could be composed
after the tier was released, silently dropping the just-recorded pass again.

**Rule:** retained serve additionally requires that every live pass index `>= retained.passCount` is still
represented in the sealed overlay tier (practically: the tier must be non-empty when
`live.passCount > retained.passCount`). Retained serve never becomes the coverage proof for releasing that
tier. If the condition fails, fall back to the existing cache/gather path, which does contain those rows.

### F3 — capacity pricing (conservative)

Retained cost is priced on the capacity `std::move` actually keeps from `admitWorkspace`'s
`notes.reserve(totalEventRows)`, i.e. **`16·E`**, not `16·R`.

- Steady peak while a replacement builds: `16·E_retained + B_cand`, with
  `B_cand = 16·E_live + 16·P + sizeof(MidiEvent)·P`.
- No `shrink_to_fit`, no allocation on promotion; earlier "max, not sum" wording is withdrawn.
- Over-cap: `retainedNotes.capacity() > kRetainedDisplaySourceNoteCapacity` (4096 notes = 65,536 B) is a
  **named refusal** (`retained_capacity`), previous envelope kept; with no envelope the behaviour is
  exactly today's. A dense take larger than the cap therefore degrades to today's hole, visibly.

### F4 — cardinality

No fixed array and no truncation point: the prefix check walks live passes, so pass count is unbounded by
construction and an over-limit case can never be silently truncated.

### F5 — diagnostics

No new RAM1-sensitive literal for observability. Reuse existing receipt vocabulary and, if a distinct
token is genuinely required, place it where an existing `.rodata.str*` carve-out already exists.
`check_ram1_budget.py` fails on **any** `variables` change (`:118`), so "unchanged" is a **measured**
result (build before/after), not an assumption. No budget re-base for observability.

### Resident-store registration

Class: derived display source, external/PSRAM-first. Cardinality: one retained envelope, global (the
producer is single). Capacity cap: 4096 notes / 65,536 B. Eviction: previous-version retention — the
envelope survives re-key and candidate mismatch and is replaced only by a newer promotion, or dropped by
identity failure, explicit cancel, or over-cap refusal.

### Candidate-only reset

Re-key and `!passesMatch` reset the **candidate** only; the retained envelope survives until its own
identity fails. `boundedDisplayCancel()` remains the one explicit full clear.

### Fixtures required before production (round 2 falsification set)

1. Capture-pass undo after promotion → named refusal, undone rows never painted.
2. Edit-pass undo/redo → same, proving the stamp covers `setEditPassState`.
3. Capacity boundary: `E == cap` retains; `E == cap + 1` refuses by name; frame equals today's behaviour.
4. Cardinality: a take with more passes than any internal guess (e.g. 20 overdubs) serves or refuses by
   name, never truncated.
5. F6: wrap append whose sealed tier was released before promotion → retained must refuse, appended rows

6. The original immediate-wrap RED stays enforced, unweakened.

### Round 2 addendum — F7/F8 (folded in; closes the review loop)

**F7 — do not rely on an enumerated restore list.** The round-2 text left "every pass-replacing
restore/hydrate/clear path" as an implementation-time enumeration, which is exactly the hidden-invalidator
class that produced F1. `Loop` already carries `uint64_t canonicalStorageGeneration` (`include/Loop.h:153`),
bumped on `resetPassTimeline` (`src/Loop.cpp:38`) and on prepared-companion/storage-ownership exchange
(`LoopPreparedCompanionHistory.cpp:77,340`), and **not** bumped by a wrap append or a state toggle.

Revised identity therefore requires **both** stamps:

- `passStateRevision_` — new, external, +4 B; enable/disable and timeline reset (F1/F2).
- `canonicalStorageGeneration` — existing; storage identity/replacement (F7).

The retained envelope serves only when both are unchanged. The enumerated-call-site requirement is
withdrawn; anything that replaces pass storage must move the existing generation, which is already the
repo's convention. Any restore path found not to move it is a defect in that path, not a retained-envelope
parameter.

**F8 — F6 needs a precise predicate, not "non-empty".** The sealed tier can hold rows belonging to a
different interval, so "tier non-empty" is necessary but not sufficient. Retained serve requires the tier
to be **unreleased for this loop** (`!sealedCapturePreviewIsCovered()`) *while* a pass was appended since
promotion; the exact accessor is fixed at implementation and proven by fixture 5. Until that fixture is
green, F6 is a contract clause without a proof, and the retained path must not be relied on to cover
appended rows.

## Round 2 correction — identity without growing `Loop` (build-gate refutation)

The round-2 mechanism (a new `passStateRevision` field on `Loop`) was **refuted by the build gate**, not
by preference. Trial edit `+8 B` on `Loop` failed:

`src/Track/TrackPlaybackRuntime.cpp:3057: static assertion failed: I5/C3: LoopPool shell 1,848 B … 1,784 -> 1,848`

`sizeof(Loop)` is a **reviewed bound** (eight external shells per allocated Track). Re-basing it to 1,856
would be a deliberate bound change for one comparison, so the field was reverted; `pio run -e
teensy41-capture-serial` then returned SUCCESS with `variables 96,192` / `padding 3,224` / `locals 34,880`
unchanged. Nothing from that attempt remains in the tree.

**Replacement mechanism — live-computed state fingerprints, zero new `Loop` state.** At promotion the
retained envelope stores two 64-bit FNV-1a digests:

- `captureStateDigest` over the first `retainedPassCount` eligible passes: `(index, PassId, state,
  committedRows)`;
- `editStateDigest` over every edit pass: `(index, EditPassId, passType, state)`.

`retainedServable` recomputes both live (O(P), allocation-free) and requires equality, together with
`owner`/`loopId`/`loopLengthTicks`, `passCount >=`, `keyEventRows`, edit count and last edit id.

Why this is stronger, not merely cheaper:

- Undo/redo **enable/disable** a pass (`setCapturePassState`, `setEditPassState`) — both digests change, so
  the envelope is refused. This closes F1/F2 without per-pass arrays and without F4's cardinality.
- A wrap **appends**; the capture digest covers only the retained prefix, so it is unchanged and serving
  continues — the behaviour the fix exists for.
- Nothing new must be enumerated: any future state transition participates by construction.
- No `Loop` growth, so the 1,848 B shell pin and RAM1 stay untouched.

**Residual risk, stated:** a 64-bit digest collision would wrongly serve. That is 2^-64 per comparison,
and is never the deciding term because pass count, row inventory, edit count and
`canonicalStorageGeneration` are compared independently. If a future reviewer wants collision-freedom, the
alternative is explicit evaluated states at declared cardinality with fail-closed refusal — a larger
contract, not a different result.

Implementation slices are unchanged in order; the previously planned `passStateRevision` bump sites are
withdrawn, and `setCapturePassState` / `setEditPassState` need no edit at all.

## Round 3 — exact predicate adopted; redo semantics resolved by evidence

Owner direction: prefer an **exact live pass-state comparison** over a 64-bit digest if the O(P) walk is
already acceptable. Agreed and adopted — the digest is withdrawn. A stale-content guard that can be exact
should not carry a probabilistic term.

**Retention identity is a bounded exact predicate over the authoritative pass metadata at the moment of
reuse, not a cached stamp.** Zero new `Loop` state; the 1,848 B shell pin is untouched.

### Exact predicate (all required)

Capture prefix, for `i < retainedPassCount`, in resolve order:

- `i`, `PassId`, `CapturePassState` (Active/Disabled), and the exact committed-row inventory term the
  result depended on (`committedChunkIds` identity — not merely a row count);

Edit list, for every entry:

- `i`, `EditPassId`, `EditPassType`, `EditPassState`;

plus `owner`, `loopId`, `loopLengthTicks`, `retainedPassCount <= live.passCount`,
`keyEventRows`, edit count, last edit id, and `canonicalStorageGeneration`.

Newly appended passes after the retained prefix are **not** compared, which is exactly what lets a wrap
keep serving; state changes *inside* the prefix refuse it.

### Redo / resurrection — decision

VERIFIED: `Loop::setCapturePassState` bumps `playbackRevision`, clears the sealed/retired display tiers on
Disable, and calls `notifyCommittedContentChanged`; it does **not** bump `canonicalStorageGeneration`
(`src/Loop/LoopCapture.cpp:176-218`). `setEditPassState` bumps only `playbackRevision`
(`src/TrackUndo.cpp:337-363`). So an undo→redo pair can return every stored field to its prior value, and
the monotonic term the round-3 note hoped for is *not* guaranteed to move.

**Decision: that is requalification by identity, not stale resurrection — provided the predicate is
exact.** If every compared field (including chunk identity) and `canonicalStorageGeneration` match, the
retained result is the deterministic output of the *current* passes, so serving it is provably identical
to rebuilding. There is no stale-content path to protect against. Adding a counter to forbid a correct
answer would be ceremony, and it is the only mechanism that would need new `Loop` state.

This is falsifiable, and must be falsified rather than asserted:

- **Positive:** after undo then redo, if the predicate requalifies, the served rows must equal an
  **independently rebuilt** frame for the same interval, note-for-note by `NoteId` and geometry. Equality
  proves "correct requalification"; any difference proves the predicate is under-specified and the
  property must be withdrawn.
- **Negative:** a state flip *without* redo must refuse, using the same fixture family.
- Residual risk to state: chunk content mutating in place without a storage-generation move. That is a
  defect in the storage convention, not a retained-envelope parameter; fixture 5 covers the reachable
  halves.

### Fixture order (owner-specified, supersedes the earlier list)

1. Capture undo invalidates — same ID/chunks/count, state flips Disabled → must not serve.
2. Capture redo requalifies — state returns Active; assert equality against an independent rebuild (see
   decision above), never "the stale object silently became valid".
3. Edit undo invalidates — same edit ID/count, state flips → refused.
4. Wrap append preserves the retained prefix — appended pass after the prefix does not invalidate.
5. Capacity boundary — retained capacity at the declared maximum is accepted and priced by actual
   capacity (`16·E`).
6. Over-cap — one beyond the cap is a named refusal; existing qualified retained content stays intact.
7. The original immediate-wrap RED stays enforced as the end-to-end case.

No production code, upload, device stimulus or commit in this round.
