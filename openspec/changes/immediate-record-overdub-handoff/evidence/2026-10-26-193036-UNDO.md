## Verified execution / ownership

`MidiButtonActions::handleUndo` gates OVERDUBBING to the Loop session undo; no global stack/Record
undo fallback follows this route. `Loop::undoOverdubSession` at session cursor0 saves live events in
its existing live-undo vector, advances capture-content generation, clears only capture.store,
rebuilds capture preview and increments captureDisplayRevision. The live branch does not call
setCapturePassState or pop a Record undo entry. This disproves that specific code path as a global
Record-undo command; it does not prove hardware stored-content/output parity.

`TrackUndo::undoOverdubSession` then calls loop.invalidateCaches and unconditional
DisplayManager::invalidateLiveDisplayCache. That call clears the held frame, committed prefix,
counts and source key. While Record's root/cache is unavailable, the display loses the held Record
base, leaving other available overlays. Live redo uses the same unconditional display invalidation.
The existing display's live/committed revision distinction and held-prefix composition must be
preserved by a repair; merely freezing the whole old frame would retain undone live rows.

Separately, Track input maintains TWO coherent inventories: Loop capture rows and the live
CaptureAdmissionStaging rows/reservations/credit counters. Track also owns pendingNotes. Actual
recordMidiEvents reserves a complete lifetime, appends both inventories, then publishes staging's
generation. Live Loop undo/redo bypass that owner: neither clears/restores Track pending notes,
staging rows, open reservations/credits/generation, pending overlap changes or append-history
metadata. Undo leaves stale staging after canonical rows clear; later input appends divergent
inventories. Held-note releases can fail to match their retained reservation once the canonical On
was removed, and another same-pitch On can remain pending-blocked. Stop reads staging counts and
raw custody separately, so this is a concrete lifecycle inconsistency, not cache hygiene.
