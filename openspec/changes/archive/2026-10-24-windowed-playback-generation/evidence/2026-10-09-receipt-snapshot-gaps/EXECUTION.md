# Record-return evidence contracts — deterministic Capture receipt and Snapshot post-step confirmation

**Scope (2026-10-09):** `windowed-playback-generation` 3.9 — readiness receipt delivery, 3.15b/c — frozen Record owner/reader observations, and the existing `Loop` Snapshot publication observer. No playback policy, Snapshot source, scheduler, admission, SD schema, or default rolling-selection change. The implementation branch is `feature/unified-rolling-playback-path` with an existing dirty tree; preserve unrelated changes. Authority: [DEC-108 — windowed publication](../../../../../docs/DECISION_LOG.md#dec-108--windowed-playback-generation-one-publication-owner-window-sized-reservation-pinned-source-retention-and-readiness-as-completed-publication), [DEC-116 — one rolling path](../../../../../docs/DECISION_LOG.md#dec-116--one-rolling-playback-path-per-sounding-slot), [readiness receipt requirement](../../specs/windowed-playback-generation/spec.md#requirement-readiness-evidence-is-delivered-where-it-is-produced). Existing owners remain `Track::stepPlaybackViewMaintenance`, `Loop::stepPendingSnapshotPublish`, and `Track::processSnapshotOwnerTurn`.

## Slice A — frozen Record terminal receipt

**Verified G0:** `Track::stepPlaybackViewMaintenance` frozen Record branch emits a `build_complete` path and calls `reportPlaybackWindowReadinessReceipt` after complete ready, but that reporter uses one process-wide DMAMEM counter at interval 16. Runs `captures/e2-lane-rows-20261009-run2` and `…-run3` have 7–8 completions, one receipt vs zero. The one run-2 receipt is `not_servable/not_servable` because `playbackWindowReadinessForSlot` exits on `!loop.hasCommittedPasses()` even when the frozen job's Capture-origin ready is complete. A row of that name cannot prove frozen readiness. `DebugSessionCapture::readinessReceiptImmediate` already has direct-when-room and Tier-A ring fallback; do not invent another delivery channel. The verifier currently accepts any receipt under transport without target, source, interval, or positive-readiness qualification.

**Transition oracle:** Real accepted Record stop leaves complete current/raw view, pending generation/LoopId-qualified job range and unpublished checkpoint. Give the same Track owner bounded grains to complete a Capture-origin ready of known `(track,slot,sourceGeneration,captureContentGeneration,coverage)` while PLAYING. Exactly on Complete, emit one Tier-A/direct-when-room receipt that names `complete_ready` / `clock_edge` (not committed `ready/current`) and carries origin, content token and coverage in an extension of the existing `DIAG,win_readiness` row. It must match the physical complete unpublished ready and job receipt and be under transport. A denied grain is `owes_build` on the frozen owner, not `not_servable`; repeated refusals may remain cadence-bounded and cannot suppress a later completion receipt. New job/slot identity cannot inherit a stale receipt; no extra Track DTCM state or one row per fill grain. Host verifier shall require a target-matching, positive source-qualified terminal receipt for the Record leg, not arbitrary `not_servable`; keep older committed-route rows parsed and judged by their own existing semantics. RED controls: previous global-16 selection suppresses the first frozen completion in a primed episode; generic `not_servable` fails source/ready assertion; withholding the Track owner yields no ready receipt. Restore and test source/interval, exact row bytes, direct/fallback Tier-A delivery, denial sampling, and RAM1/DMAMEM bound.

## Slice B — target Snapshot publication confirmation

**Verified G0:** `Track::processSnapshotOwnerTurn` calls `reportSnapshotOwnerGateRow` **before** `Loop::stepPendingSnapshotPublish`. The latter atomically stores the whole root and emits `DIAG,snapshot_unit,kind=publish` without track/slot or published revision. In both device runs the target's last `snap_gate` precedes that anonymous publication (run 2: 143.255→143.337 s; run 3: 426.952→426.973 s), and no next target owner call exists. The host verifier requires an after-stop target row with `p=sep=fc=0,hp=1,rv≠record_rv` and therefore reports unconfirmed. An anonymous publish cannot be attributed to target slot by the verifier, and extending a fixed wait alone cannot force a next owner turn.

**Transition oracle:** On a production Track Snapshot owner turn with a queued Record session-exit root, sample the selected Loop's published revision before the normal bounded `stepPendingSnapshotPublish`. On complete publication only, emit one post-step `snap_gate` receipt carrying the same target track/slot, fresh complete-root revision and post-step `p/sep/fc/hp` state. Do not emit it on incomplete/denied/stale construction or a foreign slot; duplicate owner turns cannot produce a second publication confirmation. The pre-step progress gate remains unchanged. `record_snapshot.verify_record_snapshot_progress` must fail on a pre-step-only/anonymous-publish trace and pass only when the correctly attributed post-step row follows the stop with changed `rv`. Fixture first on the real `Track::processDeferredIdleMaintenance(...Snapshot...)`/`Loop` publication route, with another slot/root activity to reject false attribution; test host verifier against synthetic lost post-step and wrong-slot cases. No partial `LoopSnapshot`, extra owner turn, repeated per-step telemetry or new persistence state. Reuse the existing `snap_gate` Tier-A/two-delivery row; record bytes/target identity and RAM1.

### Slice B — production already present; hardened and pinned

The post-step `snap_gate` receipt described by the oracle was already in the working tree from the earlier session turn (`Track::processSnapshotOwnerTurn` re-reports with post-step state when `publishedSnapshotRevision()` changed). This session closed the two residual holes:

1. **The confirmation can no longer be deduped away.** `SnapshotGateLastState` gained `publishedRevision`, and `reportSnapshotOwnerGateRow`'s change key now includes it, so a revision change is **always** named even when the pre- and post-step verdict bits happen to coincide. Without this, "the confirmation row exists" rested on the verdict bits differing rather than on the revision changing.
2. **The verifier now requires a genuine post-step confirmation.** `record_snapshot.verify_record_snapshot_progress`'s `record_session_exit_root_published` only counts a settled row that comes **after** the last row that still owed the session exit (`p`/`sep` set). A settled row preceding a further owed turn is not a confirmation of this publication, and a run whose final owner turn published with no row after it now fails instead of passing on a restatement of the demand. The check detail carries `post_step_confirmed` and `owed_index`.

Host tests: `test_a_generic_receipt_alone_does_not_answer_the_readiness_term`, `test_a_frozen_receipt_without_a_content_token_is_not_a_completion`, `test_the_frozen_receipt_parser_reads_the_emitters_field_order`, `test_a_confirmation_before_the_work_was_owed_is_not_a_confirmation` (plus the pre-existing `test_snapshot_publication_requires_target_post_step_receipt`). Native: the pre-existing `test_deferred_record_publication_queues_the_record_session_exit_snapshot` already requires exactly one target-qualified confirmation from the final production owner turn and no repeat on a duplicate turn.

### RAM1 — the new literals cost 4 KB until they are routed (recorded for the rule's list)

The first default build failed the budget check: `variables 96,192 -> 100,288` (+4,096, locals 34,880 -> 30,784) with ITCM `code` **unchanged** — the `_VectorsRam`/periodictable align-edge snap the [`Teensy-RAM1-Bank-Overflow`](../../../../../.cursor/rules/Teensy-RAM1-Bank-Overflow.mdc) rule documents. Measured cause, one literal at a time:

- the ring-path format string (`emitCapPrintf`) and the tier tag prefix (`CaptureLineTier.h`) are `.rodata.str*`, and `.rodata` is DTCM in this script. Both were routed to memory-mapped FLASH: the format via a file-scope `PROGMEM` array (`SC_FMT` already does this for the direct path via `PSTR`), the tag prefix via `CaptureLineTier::frozenReadinessTagPrefix()`, declared in the header for the target and defined `PROGMEM` in `DebugSessionCapture.cpp` (the header cannot carry the attribute — the compiler reports a section type conflict — and the host build takes the header's inline literal).
- Result: `variables 96,192` **exactly**, `code 390,360`, padding 2,856 in both `teensy41-capture-serial` and `teensy41-capture-serial-window-qualification`. **No `scripts/ram1_budget.json` re-base and no linker-script carve-out.** The wider alternative tried first — a `*DebugSessionCapture*.o(.rodata.str* ...)` carve-out in `linker/imxrt1062_t41_lcr.ld` — moved the whole TU's strings and overshot to `variables 92,096`; it was reverted in favour of the two narrow routes above.
