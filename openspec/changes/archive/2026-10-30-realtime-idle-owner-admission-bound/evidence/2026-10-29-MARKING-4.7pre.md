## What landed

Three marks, at the three transitions, on the **real** capture path in `src/Track/TrackCaptureInput.cpp`:

| transition | site | call |
|---|---|---|
| NoteOn | where the occupancy phase (`holdStart`) is computed | `markOverdubCoverageNoteOn(holdStart)` |
| held advancement | each playback note-on a held key crosses | `markOverdubCoverageHeldAdvance(holdStart)` |
| NoteOff | before the live delta is computed | `markOverdubCoverageSpan(prior.tick, newEvt.tick)` |
| stop finalization | before the closing delta is computed | `markOverdubCoverageSpan(prior.tick, phaseTick)` |

`Loop::markOverdubCoverageSpan` takes the pair and derives the length itself, treating `end <= start` as
a loop wrap (`loopLength - start + end`), so a wrapped note seals both the end and the start tiles.

All three are **marks only**: no derivation, no allocation, `O(tiles touched)`, and they return the
number of newly required tiles so a caller can tell "new work appeared" from "already required".

## Why marking first

Wiring the prerequisite *decisions* (occupancy refusal, held participation, span finalization) changes
behaviour on the capture path and cannot be validated without tile preparation actually running. Marking
is additive: it populates required coverage and nothing consumes it yet, so the tree stays green and the
next slice has real demand to serve.
