## The fork this boundary leaves

Two explanations fit "worked before, silent after, still silent after the code was reverted":

1. **Code-path regression.** A DEC-191 behavioral delta removed an accidental-but-necessary playback or
   source-servicing opportunity. Reverting the call sites should then have restored playback; the 01:30
   report says it did not, which weakens — but does not falsify — this fork, because the revert image may
   not have been the exact pre-DEC-191 tree.
2. **Card-state regression.** The broken runs rewrote the slot body. The 01:55 entry records a deferred
   save writing a **passes-only body with no root** (`root_rev,0`, `snapshot_unit` 0, paint 384 of 672), and
   that state is inherited by every later image. Reverting code cannot undo a persisted body.

The honest starting point is therefore: **do not assume the code caused it.** A pre-regression card backup
exists — `captures/sd-backup-20261029_001835/` (1035 files, manifest with CRC32 + SHA-256) was taken at
00:18, before the first-bad flash at 01:12. That makes the fork cheap to decide on hardware.

## Card-state caution

The SD card is user data. Comparing or restoring a slot body is a **write** unless it is done on a
quarantined copy; it needs explicit permission in the session that performs it
([`Destructive-SD-Operations.mdc`](../../../../.cursor/rules/Destructive-SD-Operations.mdc)). Prefer the
read-only path first: dump the current slot body and diff its pass/root inventory against the 00:18 backup,
without writing anything to the card.
